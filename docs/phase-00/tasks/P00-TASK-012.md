## Interfaces implémentées

`HarborAdapter` expose `prepare → invoke → collect` derrière le SDK provider-neutral. La préparation valide le snapshot Task 10 avant Harbor et impose `harbor run --config`, une tentative, une concurrence, un agent oracle et aucun dataset distant.

`HarborExecutionCapture` conserve les bytes bruts, le code retour Harbor, la reward, l’artefact de frontière d’exception, l’inventaire fermé de fixture, le discriminant souverain et les six obligations de phase. Aucune classe Harbor ou Docker ne traverse la frontière canonique. Le chemin qualifié réel exige un `HarborResourceObserver` injecté avant/après Harbor; sans cet observateur indépendant, l’exécuteur retourne une preuve `INFRA` et n’exécute pas Harbor.

`GitSpaceHarborEnvironment` est le point d’extension Harbor supporté (`environment.import_path`) : il lie l’image de tâche et le sidecar egress préqualifiés par références Docker digest-bound et refuse tout réseau autre que `no-network`. Le worker reçoit un `PYTHONPATH` minimal vers le package interne afin que cet import fonctionne dans le venv Harbor exact.

`HarborReplayRecord` v2 ajoute :

- `exception_discriminant`, séparé de `exception_type_diagnostic`;
- `stage_obligations` fermé par `environment_started`, `agent_setup_completed`, `agent_execution_started`, `agent_execution_completed`, `verifier_started`, `verifier_completed`;
- cleanup fermé par `process_group_absent`, `temp_root_absent`, `containers_absent`, `networks_absent`, `derived_images_absent`, `foreign_resources_untouched`;
- références d’image environnement et sidecar liées à leurs digests;
- artefact CAS `exception_boundary` re-hashé avant classification.
- JobConfig et TrialConfig effectifs revalidés après sérialisation Harbor : une tâche exacte, un oracle, une tentative, aucun regrade/modificateur, `trial_name` séparé de l’UUID et extension d’environnement exacte;
- inventaire CAS fermé de `source-manifest.json` et des sept fichiers runtime, avec hash/taille/mode, et chemin de tâche lié au JobConfig;
- timings de phases comparés au `trial_result`; pour `agent_timeout_exact`, les sorties verifier peuvent être absentes, tandis qu’un timeout verifier reste `INFRA`.

## Classification souveraine

La précédence est `POLICY → INFRA → TIMEOUT → PASS|FAIL`.

`TIMEOUT` exige exactement `agent_timeout_exact`, le stage `agent_execution`, reward absente, environnement démarré, setup terminé, exécution démarrée mais non terminée, verifier non démarré et intégrité/cleanup fermés. Le nom `AgentTimeoutError` dans un JSON ne suffit pas.

`AgentSetupTimeoutError`, `VerifierTimeoutError`, `EnvironmentStartTimeoutError`, `other_exception`, stage inconnu, frontière absente/divergente, reward malformée, cardinalité incorrecte, code Harbor non nul, CAS divergent ou cleanup incomplet donnent `INFRA`.

Une reward `0` n’est `FAIL` que pour `status_control`; une reward oracle `0` est un candidat de tâche invalide, pas un échec agent.
